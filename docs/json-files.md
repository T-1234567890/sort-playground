# JSON Files

This repository uses JSON files for algorithm metadata, translations, and generated Labs data.

Use this document as the default rulebook whenever you add or edit any `.json` file in the project.

## 1. General Rules

- Use UTF-8 text encoding.
- Use spaces for indentation.
  Current repo convention is `2` spaces.
- Use double quotes for all keys and string values.
- Do not use comments.
  JSON does not support `//` or `/* */`.
- Do not leave trailing commas.
- Keep object keys stable and descriptive.
- End files with a newline.

## 2. When To Use JSON Here

JSON is used for:

- algorithm metadata
  - `src/algorithms/<slug>/meta.json`
- translation files
  - `src/i18n/en.json`
  - `src/i18n/zh.json`
- generated Labs data
  - `public/data/benchmark-ranking.json`
  - `public/data/benchmark-languages.json`
  - `public/data/community-ranking.json`
  - `public/data/event-ranking.json`

Do not use JSON when the file needs executable logic.

Use:

- `steps.ts` for visualization behavior
- `*.py`, `*.rs`, `*.c`, or community language files for implementations
- Markdown for contributor-facing documentation

## 3. Algorithm `meta.json`

Each algorithm folder must include a `meta.json`.

Example:

```json
{
  "name": "Example Sort",
  "category": "classic",
  "complexity": "O(n log n)",
  "spaceComplexity": "O(n)",
  "stability": "Stable",
  "description": "A concise description of the algorithm.",
  "author": "T-1234567890",
  "contributors": ["T-1234567890"],
  "added": "2026-04-20",
  "keywords": ["classic", "fast"],
  "funRank": 3
}
```

Important rules:

- `category` must be one of:
  - `classic`
  - `weird`
  - `meme`
- `added` should use ISO-style date format:
  - `YYYY-MM-DD`
- Keep `description` concise and factual.
- `author` and `contributors` should use GitHub usernames, not display names.
  The UI uses those values to build GitHub links and avatar/icon URLs.
- If the algorithm should not be benchmarked, state it explicitly:

```json
{
  "benchmark": false,
  "special": "no-benchmark"
}
```

## 4. Translation JSON

The translation files are:

- `src/i18n/en.json`
- `src/i18n/zh.json`

Rules:

- Keep the same key structure in both files.
- Add keys to both locales in the same change.
- Prefer nested objects over long flat key names.
- Keep labels short when they appear in buttons, tabs, or badges.
- If a UI string changes, update the JSON instead of hardcoding text in a component.

Example:

```json
{
  "languageBenchmark": {
    "title": "More Language Benchmark",
    "note": "These results do not affect the main benchmark ranking."
  }
}
```

## 5. Generated Data JSON

Files under `public/data/` are data outputs for the frontend.

Current generated files:

- `benchmark-ranking.json`
- `benchmark-languages.json`
- `community-ranking.json`
- `event-ranking.json`

Rules:

- Treat generated data as schema-driven.
- Do not invent fields casually.
- If you need a new field, update:
  - the generator script
  - the frontend type in `src/core/types.ts`
  - the UI that reads it
- Keep naming consistent across files.
  Prefer `slug`, `name`, `status`, `metadata`, and `results` when those concepts already exist.

## 6. Arrays vs Objects

Use an array when order matters:

```json
[
  { "slug": "quick-sort" },
  { "slug": "merge-sort" }
]
```

Use an object when you need named lookup keys:

```json
{
  "python": { "small": 0.12, "medium": 1.34 },
  "rust": { "small": 0.03, "medium": 0.21 }
}
```

In this repository:

- ranking lists are usually arrays
- language buckets, metadata groups, and result maps are usually objects

## 7. Keep Schemas Predictable

When extending an existing JSON format:

1. reuse current names if the concept already exists
2. prefer additive changes over renaming old fields
3. avoid mixing multiple shapes for the same field
4. keep optional fields truly optional
5. document the new field in the relevant docs

Bad:

```json
{
  "score": 91,
  "scoreValue": 91,
  "points": 91
}
```

Good:

```json
{
  "score": {
    "composite": 91
  }
}
```

## 8. Validation Checklist

Before committing a JSON change:

1. confirm the file is valid JSON
2. confirm indentation and quotes match repo style
3. confirm both locales were updated if it is i18n
4. confirm related TypeScript types still match
5. run:

```bash
npm run build
```

If the file is generated by CI, also make sure the generator and UI still agree on the schema.

## 9. Practical Repo Guidance

If you are adding a new purpose-specific JSON file:

1. decide whether it is source content, translation content, or generated data
2. place it in the correct area:
   - `src/algorithms/*` for algorithm metadata
   - `src/i18n/` for translations
   - `public/data/` for generated Labs data
3. define or update the matching TypeScript type
4. document the format where contributors will look for it

When in doubt, follow the shape already used by nearby files instead of inventing a new style.
